# 14. Real Design System Case Studies

## Definition

A design system **case study**, for interview purposes, is not a
feature-by-feature description of what a system contains — it's an
explanation of what **constraint** shaped that system's architecture, and
why a different constraint would have produced a different system. Material
Design, Polaris, Carbon, and Radix all solve "consistent, accessible UI at
scale," but each was built against a different forcing function — multi-OS
distribution, third-party extensibility, enterprise governance, headless
reusability — and that forcing function, more than any stylistic
preference, explains the architectural decisions each one made.

## Problem Statement

Candidates who've only read component documentation can list what a system
has (Polaris has an `<IndexTable>`, Carbon has a Sass-to-token migration
story) but can't answer the question a senior interview actually asks:
*why does Polaris care so much about App Bridge and accessibility
specifically, in a way that, say, a purely internal system wouldn't need
to?* Reciting features is memorization; explaining constraints is judgment,
and judgment is what a Staff-level design systems interview is testing.
This chapter is built to answer "X chose Y because of Z constraint" for
each system, not "X has feature Y."

## Why Does This Exist?

Comparative case studies exist in this handbook because every architectural
decision earlier chapters cover — token layering
([Design Tokens](/chapters/design-tokens)), styling approach
([Styling Architecture](/chapters/styling-architecture)), component API
shape ([Component Architecture](/chapters/component-architecture)) — was
made by a real team under a real constraint, and the fastest way to
internalize *why* a given tradeoff is usually chosen in practice is to see
the same category of decision made differently by systems with different
constraints, and understand what forced the difference.

## Historical Context

The systems in this chapter span roughly a decade of design system
evolution and represent three distinct eras:

**The multi-platform-consistency era (2014–2017).** Google's Material
Design (2014) was among the first design systems to treat "one visual and
interaction language across every Google product and platform" as an
explicit, published specification rather than an implicit convention.
IBM's Carbon and Adobe's Spectrum emerged from the same pressure inside
their own multi-product portfolios shortly after.

**The product-scale-and-accessibility era (2017–2020).** As React
matured as the dominant UI framework, product companies running large
B2B/B2C surfaces — Shopify (Polaris), Atlassian (Atlassian Design System)
— built systems where the driving constraint was less "match our brand
everywhere" and more "our product is complex enough, and our users
professional enough, that inconsistency directly costs revenue and
support tickets."

**The headless/open-source era (2020–present).** Radix UI (2020) and
Chakra UI (2019) represent a structural break from what came before: rather
than a single company publishing its own internal system, these are
open-source projects built explicitly to be a *foundation* other
companies' design systems get built on top of. This is also the era that
produced shadcn/ui (2023), which isn't a traditional design system at all
but a code-generation pattern built directly on Radix — arguably the most
consequential development in component-library distribution of the last
several years, and worth understanding precisely because it breaks the
"install a package" mental model every earlier system in this chapter
assumes.

## How It Works Internally

Rather than one shared "internal mechanism" (these are eight different
systems), this section walks through the specific mechanism that makes
each system's defining constraint concrete — the thing you'd point to if
an interviewer asked "how, specifically, does that actually work?"

### Material Design — tokens as the cross-platform contract

Google ships Material across Android (Kotlin/Jetpack Compose), iOS (Swift),
Web (Material Web Components / MUI for React), and Flutter — four
completely different rendering engines with no shared runtime. The
mechanism that makes "one design language" possible across that split is
that Material's *source of truth* is not code in any one of those
languages — it's a token specification (the [Design Tokens](/chapters/design-tokens)
concept, at Google's original scale) that each platform's implementation
consumes independently. **Material You** (introduced with Android 12)
pushed this further: dynamic color extraction from a user's wallpaper
generates a full tonal palette *at runtime, per device*, meaning the token
values themselves are no longer even fixed at build time on Android — the
system had to be architected so tokens are a resolvable reference, not a
baked-in constant, from the start.

### Atlassian Design System — tokens for multi-product B2B consistency

Atlassian's constraint is different: not multiple OSes, but multiple
*products* (Jira, Confluence, Trello, Bitbucket) that need to feel like one
company's software while each having enough product-specific complexity
(Jira's issue workflows, Confluence's document editing) that a rigid,
one-size-fits-all component set would fight each product's actual needs.
Atlassian's token architecture is built around this with an explicit
semantic layer — tokens like `color.background.brand.bold` resolve
differently per product/theme but the *name* a component author reaches
for is shared across all of them, which is what lets a Jira engineer and a
Confluence engineer both build on the same design system without
coordinating on raw color values.

### Shopify Polaris — the App Bridge constraint

Polaris has a constraint essentially none of the other systems in this
chapter share: its component library is used not only by Shopify's own
engineers, but by **thousands of independent third-party companies**
building apps that live *inside* the Shopify admin, embedded via iframe.
Shopify doesn't control these developers' engineering quality, their
release cadence, or their commitment to accessibility — but a merchant
using a third-party app inside their Shopify admin experiences it as part
of Shopify's product. This is why Polaris invests unusually heavily in (a)
strict, enforced accessibility standards (a third-party app's inaccessible
custom widget reflects on Shopify, not just the app developer) and (b)
**App Bridge**, a JavaScript bridge library that lets embedded third-party
apps render Polaris-consistent UI (title bars, navigation, modals) *without
that app needing to load Polaris's own React components directly* — App
Bridge works by having the embedded app send structured messages
(postMessage-based) to the parent Shopify admin frame, which renders the
actual Polaris UI natively in the host frame. No other system in this
chapter has to solve "make a UI feel consistent when we don't control the
runtime rendering it."

### Adobe Spectrum and React Aria — decoupling behavior from skin

Adobe's constraint is internal multi-product consistency at a scale
comparable to Atlassian's (Photoshop, XD, Creative Cloud web, Adobe
Express), but the mechanism Adobe chose to solve it is the most influential
thing in this chapter for the wider React ecosystem: Adobe split their
system into **React Spectrum** (the visually-styled, Adobe-branded
component layer) built on top of **React Aria** (unstyled, fully accessible
behavior hooks — keyboard interaction, focus management, ARIA attribute
wiring — with zero visual opinion) and **React Stately** (framework-agnostic
state management for those same interaction patterns). Adobe open-sourced
React Aria and React Stately *independently* of React Spectrum. The reason
this mattered beyond Adobe: accessible interaction behavior for something
like a combobox or a date picker is extraordinarily hard to get right (see
[Accessibility](/chapters/accessibility)) and almost entirely reusable
across any visual design — by decoupling the hardest, least
brand-specific part of the problem from Adobe's own visual skin, React Aria
became genuinely useful to companies with completely different visual
languages, which is exactly why it's now used far outside Adobe.

### IBM Carbon — Sass to tokens as a real migration story

Carbon is instructive specifically because it's a system that *changed its
own styling architecture in production*, which almost none of the
marketing-page case studies talk about. Carbon originally built its
theming on Sass variables and maps — workable for a single build-time
theme, but brittle for runtime theming (switching between IBM's light,
dark, and multiple brand themes without a full rebuild) and disconnected
from Figma, where designers were working in Figma Variables, not Sass.
Carbon's move to a token-driven architecture backed by CSS custom
properties (directly paralleling the general Sass-vs-CSS-Variables tradeoff
covered in [Styling Architecture](/chapters/styling-architecture)) let
theme switching happen at runtime via a `data-theme` attribute swap instead
of a separate build per theme, and gave Carbon a direct token-sync path to
Figma Variables ([Collaboration with Designers](/chapters/collaboration-with-designers)).
This is a concrete, real example of a system paying down architectural debt
at scale rather than a green-field decision — worth citing specifically
when an interviewer asks about migrating an existing system's styling
approach.

### Ant Design — comprehensive over primitive, for a specific market reason

Ant Design's defining trait relative to most systems in this chapter is
that it is **maximally opinionated and comprehensive** — a huge component
set (60+ components including complex ones like `Transfer`, `Cascader`, and
full-featured data-entry forms) with strong default styling, rather than
the "small set of unstyled primitives" philosophy of Radix or React Aria.
This isn't arbitrary — Ant Design grew out of Alibaba's internal enterprise
software ecosystem, where the dominant need was for many internal teams to
ship complex admin/back-office tooling *fast*, with consistent behavior out
of the box, and relatively less need for deep brand-specific visual
customization per team. A comprehensive, strongly-opinionated system is the
right tool for that constraint the same way a primitives-only system is the
right tool for a company that needs many different visual brands built on
one behavioral foundation.

### Chakra UI — accessibility as the default, not an add-on

Chakra's mechanism worth naming specifically: unlike systems that add
accessibility as a checklist applied to already-designed components, Chakra
built its component APIs with accessible props (e.g., built-in `isInvalid`,
`aria-*` prop pass-through, and description/error-message wiring baked
into form components from the start) as the default developer experience,
not an opt-in. Its influence on the wider React community was less about
any single technical innovation and more about *normalizing the
expectation* that a community, open-source component library should be
accessible by default — a bar that raised what developers expected from
every subsequent library, including commercial ones.

### Radix UI and shadcn/ui — headless taken to its logical extreme, and what came after

Radix is the purest expression of the headless philosophy in this chapter:
components ship **zero visual styling** — no CSS at all — and expose only
behavior, state, and correct ARIA wiring, with styling entirely the
consumer's responsibility via data attributes (`[data-state="open"]`) that
Radix components expose for the consumer to hook their own CSS into. This
is a deliberate architectural bet: rather than trying to be a standalone
visual design system that every company adopts wholesale, Radix bet on
being the *foundation underneath* other companies' visual design systems —
you build your own visual layer on top of Radix's behavior layer, the same
split React Spectrum makes on top of React Aria.

That bet paid off in a specific, highly current way: **shadcn/ui** (2023)
is not a component library you `npm install` at all — it's a CLI that
*copies* pre-built, Radix-based component source code directly into your
own repository, styled with Tailwind, which you then own and can modify
freely rather than being constrained by whatever a published package
exposes. shadcn/ui works *because* Radix already solved the hard, reusable
part (accessible behavior) — shadcn/ui only had to add the visual styling
layer and the distribution mechanism (copy-paste-as-a-package-manager),
which would have been an enormous undertaking if it also had to build
accessible listbox/combobox/dialog behavior from scratch. This is precisely
the Adobe Spectrum/React Aria pattern playing out a second time in the
ecosystem, and it's the reason "Radix vs. a standalone system" is now a
somewhat outdated framing — Radix increasingly *is* the behavior layer
other systems, including ones you'd build yourself, sit on top of.

Reading the quadrants: most product-company systems (Material, Polaris,
Spectrum, Carbon, Atlassian) sit in the styled-and-internally-governed
quadrant because their job is enforcing *one company's* brand — governance
stays centralized even when the code is open-sourced for transparency.
Ant Design and Chakra sit in styled-and-open because they're
community-facing products in their own right, meant for many unrelated
companies to adopt as-is. Radix (and React Aria, which Adobe deliberately
extracted out of Spectrum into its own quadrant) sit in headless-and-open
because their value *is* being a shared foundation, not a finished brand —
and the fourth quadrant is nearly empty in practice because a headless
system with no external reuse forfeits the main reason to go headless at
all.

## Real-World Example

Consider a concrete scenario an interviewer might pose: *"You're starting a
design system for a new B2B SaaS product used by five different internal
teams, each wanting some visual flexibility for their own sub-product, and
you have three engineers and six months."* Walking through why each case
study is or isn't the right reference point demonstrates the comparative
judgment this chapter is trying to build:

- **Not Ant Design's approach** — its comprehensive, strongly-opinionated
  component set optimizes for internal teams that *don't* need much visual
  divergence, which conflicts with the stated need for per-team
  flexibility.
- **Not a from-scratch Spectrum/Carbon-style build** — those systems
  represent years of dedicated design-systems-team investment at large
  companies; three engineers in six months cannot replicate that maturity,
  and shouldn't try.
- **Closer to the Radix-on-top model** — build a thin internal visual
  layer on top of Radix's already-solved accessible behavior (or adopt
  shadcn/ui's copy-in components as the starting point), which gets
  correct accessibility and interaction behavior essentially for free and
  lets the three engineers spend their limited time on the one thing that
  actually needs to be custom: the shared visual token layer and the
  handful of composite components specific to the product.
- **Borrow Atlassian's semantic token pattern**, not its component count —
  the specific idea of a semantic token layer that lets five sub-products
  share underlying values while resolving differently per team is directly
  transferable at any scale, unlike Atlassian's much larger component
  library, which isn't.

This is the kind of synthesis — not "which system is best" but "which
system's *constraint* matches mine closely enough that its solution
transfers" — that separates a memorized feature list from real judgment in
an interview.

## Implementation Example

Case-study chapters are comparative rather than component-building
chapters by nature, but the architectural patterns discussed above are
concrete enough to show in code. Two representative examples: Adobe's
behavior/style split (the React Aria pattern), and Radix's data-attribute
styling hook (the mechanism that makes "headless" actually stylable).

```tsx
// The Adobe/React Aria pattern: a hook owns state + behavior + a11y
// wiring; the component owns only markup and visual styling. This is
// the literal mechanism behind "React Aria works outside Adobe" —
// nothing in useToggleButtonState or useToggleButton is Spectrum-specific.
import { useToggleState } from "react-stately";
import { useToggleButton } from "react-aria";
import { useRef } from "react";

function ToggleButton(props: { children: React.ReactNode }) {
  // react-stately: framework-agnostic state machine for "pressed/not"
  const state = useToggleState(props);
  const ref = useRef<HTMLButtonElement>(null);

  // react-aria: wires keyboard handling, aria-pressed, focus visibility —
  // all the accessibility behavior a toggle button needs, with zero
  // opinion about how it looks.
  const { buttonProps } = useToggleButton(props, state, ref);

  return (
    // Every visual decision — the class name, the color, the border —
    // is entirely up to the consumer. This same hook pair could back a
    // Spectrum-styled button, an Ant-styled button, or your own.
    <button
      {...buttonProps}
      ref={ref}
      className={state.isSelected ? "toggle toggle--pressed" : "toggle"}
    >
      {props.children}
    </button>
  );
}
```

```tsx
// The Radix pattern: headless primitives expose STATE via data
// attributes on the rendered DOM node, which is the actual mechanism
// that lets a fully unstyled component still be stylable with plain
// CSS — no className logic, no runtime style computation needed.
import * as Dialog from "@radix-ui/react-dialog";

function ConfirmDialog({ open, onOpenChange, children }: {
  open: boolean;
  onOpenChange: (open: boolean) => void;
  children: React.ReactNode;
}) {
  return (
    <Dialog.Root open={open} onOpenChange={onOpenChange}>
      <Dialog.Portal>
        {/* Radix sets data-state="open" | "closed" on this element
            itself — CSS below targets it directly, no JS-computed
            className string needed. */}
        <Dialog.Overlay className="dialog-overlay" />
        <Dialog.Content className="dialog-content">
          {children}
          <Dialog.Close aria-label="Close">×</Dialog.Close>
        </Dialog.Content>
      </Dialog.Portal>
    </Dialog.Root>
  );
}
```

```css
/* This is the whole styling contract Radix exposes: state as a data
   attribute, animation driven by CSS alone. A shadcn/ui-generated
   component is, structurally, exactly this pattern with Tailwind
   utility classes instead of hand-written CSS. */
.dialog-content[data-state="open"] {
  animation: contentShow 150ms ease-out;
}
.dialog-content[data-state="closed"] {
  animation: contentHide 100ms ease-in;
}
```

## Advantages

Rather than one shared "advantages" list, the advantage each system offers
is a direct payoff of its own constraint — worth being able to state
per-system in an interview:

- **Material Design**: one specification governs four platforms, so brand
  and interaction consistency doesn't degrade as Google adds new surfaces.
- **Atlassian Design System**: semantic tokens let genuinely different
  products (Jira vs. Confluence) share an underlying design language
  without a rigid shared component set forcing product compromises.
- **Shopify Polaris**: App Bridge extends brand and accessibility
  consistency into surfaces Shopify doesn't even control the runtime of —
  a reach no purely-internal system needs or has.
- **Adobe Spectrum / React Aria**: decoupling behavior from skin turned an
  Adobe-internal investment into a genuinely reusable industry asset,
  which is a rare outcome for design system work.
- **IBM Carbon**: proved a large system can migrate its core styling
  architecture (Sass to tokens) in place without a full rewrite.
- **Ant Design**: a comprehensive, opinionated set gets many internal
  teams to a consistent, complex admin UI fast, with minimal
  per-team decision-making overhead.
- **Chakra UI**: accessible-by-default APIs raised the baseline expectation
  for the whole open-source React component ecosystem.
- **Radix UI**: became reusable *underneath* nearly any visual system,
  including ones (like shadcn/ui) built years after Radix itself shipped.

## Disadvantages

- **Material Design**: strict cross-platform token discipline can feel
  constraining to teams wanting platform-native visual idioms (an iOS team
  wanting to feel more like iOS than like Android).
- **Atlassian Design System**: semantic-token flexibility across products
  can still produce visible inconsistency if product teams interpret
  shared tokens loosely — governance overhead scales with product count.
- **Shopify Polaris**: App Bridge and strict accessibility requirements are
  real friction for third-party developers who'd otherwise want more
  visual freedom in their embedded apps.
- **Adobe Spectrum / React Aria**: the behavior/style split means adopting
  React Aria alone still requires a real internal investment to build the
  visual layer — it removes the hardest problem, not all the work.
- **IBM Carbon**: large-scale migrations (Sass to tokens) are genuinely
  expensive and slow, even when the end state is clearly better.
- **Ant Design**: its opinionated defaults are exactly what makes deep
  visual customization for a distinct brand comparatively harder than with
  a primitives-first system.
- **Chakra UI**: a runtime CSS-in-JS foundation (historically) carries the
  performance tradeoffs covered in [Performance](/chapters/performance)
  and [Styling Architecture](/chapters/styling-architecture).
- **Radix UI**: zero built-in styling means a consumer gets nothing
  visually usable out of the box — 100% of visual design work is still the
  adopting team's responsibility.

Large product companies pick their reference point based on which
constraint matches their own, not which system is "best" in the abstract.
A company entering **multiple platforms** (native mobile + web) studies
Material's token-as-cross-platform-contract approach, because that's the
one problem Material had to solve that most single-platform systems never
face. A company running a **platform with third-party developers building
into it** — the way Shopify, and increasingly companies like Notion or
Figma with their own plugin ecosystems, do — is the only real audience for
Polaris's App Bridge pattern specifically, because "consistency in a
runtime you don't control" is a rare, specific problem. A company planning
to **modernize an aging styling architecture without a rewrite** studies
Carbon's Sass-to-tokens migration, because it's one of the few
publicly-documented examples of that exact transition happening at scale
and surviving.

The **Radix/React Aria pattern** — headless behavior with the visual layer
built separately — has become the default starting point for new systems
built in the last few years specifically because it front-loads the
hardest, least-reusable-if-you-get-it-wrong part of the problem
(accessible interaction behavior) onto a battle-tested foundation, and
lets a small team spend its limited engineering time on the one thing that
actually has to be custom to their brand: the visual layer. This is also
precisely why shadcn/ui's copy-paste-not-install model gained so much
traction — it packages that same Radix-foundation decision as a starting
point you fully own, rather than a dependency you're constrained by.

## Tradeoffs

- **Cross-platform consistency (Material) vs. platform-native feel.**
  Enforcing one visual language everywhere trades away the ability for
  each platform's UI to feel idiomatically native to that platform's own
  users.
- **Comprehensive/opinionated (Ant Design) vs. primitives-only (Radix).**
  A comprehensive system gets teams moving fast with less decision fatigue
  but makes deep customization harder; a primitives-only system maximizes
  customization but requires every adopting team to build (or separately
  adopt) a visual layer before it's usable.
- **Open governance vs. centralized control.** Community-governed systems
  (Chakra, Ant Design, Radix) benefit from broad external contribution and
  scrutiny but move on a consensus-driven timeline; centrally-governed
  internal systems (Spectrum, Polaris) move at the pace one team decides,
  at the cost of external input.
- **Extending reach into third-party runtimes (Polaris) vs. staying
  simple.** App Bridge's reach into embedded third-party apps is a real
  capability almost no other system needs to build or maintain — it's
  additional permanent complexity that only pays off if you actually have
  a third-party app ecosystem.
- **Migrating in place (Carbon) vs. rewriting.** An in-place styling
  architecture migration preserves component API stability for consumers
  but is slower and riskier than a clean rewrite; a rewrite is faster to
  execute but breaks every existing consumer at once.

## Performance Considerations

Performance priorities differ visibly by constraint too. Material's
runtime dynamic theming (Material You) has to resolve tonal palettes
on-device without noticeable UI lag on every theme change. Polaris,
serving merchant-facing admin surfaces used all day by professional
retailers, treats interaction responsiveness (covered generally in
[Performance](/chapters/performance)) as tied directly to accessibility
outcomes — a sluggish, inaccessible admin tool costs merchants real
support time. Radix and React Aria, being headless, have comparatively
little *visual* rendering cost of their own to optimize — their
performance profile is almost entirely about efficient event handling and
avoiding unnecessary re-renders in their state hooks, since the actual
paint cost belongs to whatever visual layer sits on top.

## Scalability Considerations

Scale means something different per system's constraint. For Material,
scale is *platform count* — the architecture has to keep working as Google
adds new device categories (foldables, wearables) without re-deriving the
token contract each time. For Atlassian and Adobe, scale is *product
count* — the semantic token layer and the Aria/Spectrum split both exist
specifically so adding a new product doesn't require inventing a new
design system from scratch. For Polaris, scale is *third-party developer
count* — thousands of independent app developers, each shipping on their
own schedule, is a governance and consistency challenge no single-team
system faces. For Radix, scale is *reuse count across unrelated
companies* — its API stability matters disproportionately because
breaking changes ripple into every downstream system (including shadcn/ui
generated code already sitting in thousands of repositories) rather than
just Radix's own team's product.

## Common Mistakes

<Callout type="danger" title="Treating 'headless' and 'primitives-only' as automatically better">
  Radix's headless approach is the right answer to *Radix's* constraint —
  being a reusable foundation for many unrelated visual systems. It is not
  automatically the right choice for a three-person internal team that
  needs a usable, consistent UI shipped next quarter with no separate
  visual-layer investment. Recommending headless-everywhere without
  checking whether the team has the capacity to build the visual layer is
  a common interview misstep.
</Callout>

<Callout type="danger" title="Describing Polaris's App Bridge as 'just their component library'">
  App Bridge is a fundamentally different mechanism from Polaris's React
  components — it's a cross-frame messaging protocol for embedded
  third-party apps that don't load Polaris's React code at all. Conflating
  the two misses the entire point of why Polaris needed it.
</Callout>

<Callout type="danger" title="Assuming Ant Design's opinionated scope is a legacy/outdated approach">
  A comprehensive, opinionated component set isn't an earlier evolutionary
  stage that primitives-only systems superseded — it's a still-current,
  deliberate choice that's correct for the specific constraint (many
  internal teams, fast shipping, low need for per-team visual divergence)
  Ant Design was built for.
</Callout>

<Callout type="danger" title="Not knowing the shadcn/ui-Radix relationship">
  In current interviews, not being able to explain that shadcn/ui is
  Radix-based components distributed via copy-paste rather than npm
  install (and why that distribution model exists — full ownership, no
  version-lock constraint) reads as out-of-date knowledge of the current
  React component ecosystem.
</Callout>

## Best Practices

- When referencing a case study in an interview, always name the
  *constraint* first, then the mechanism that solved it — not the feature
  list.
- Use Material for cross-platform token questions, Polaris for
  third-party-extensibility questions, Adobe/React Aria for
  behavior-vs-style-decoupling questions, and Carbon for
  styling-architecture-migration questions — match the case study to the
  specific axis the question is probing.
- Cite the Radix-to-shadcn/ui relationship specifically when discussing
  current (not historical) component distribution trends — it's the most
  interview-relevant recent development in this space.
- When comparing systems, always state at least one concrete "when NOT to
  choose it" — a case study answer that only lists advantages reads as
  memorized marketing copy, not engineering judgment.
- Tie each system back to a concept from earlier chapters where relevant —
  Carbon to [Styling Architecture](/chapters/styling-architecture), Radix
  and Adobe to [Component Architecture](/chapters/component-architecture)
  — to demonstrate the case study isn't isolated trivia but an application
  of the same principles.

## Interview Questions

<InterviewQuestion q="Why did Adobe split React Spectrum into React Spectrum, React Aria, and React Stately instead of shipping one library?">
  **What the interviewer is testing:** Understanding of the
  behavior/state/style separation and why it was strategically valuable
  beyond Adobe's own needs.

  **Poor answer:** "To make the code more organized."

  **Good answer:** Explains React Aria owns accessible behavior, React
  Stately owns framework-agnostic state, and React Spectrum owns Adobe's
  visual styling on top of both.

  **Excellent senior answer:** Adds the strategic reasoning — accessible
  interaction behavior is the hardest and most broadly reusable part of
  the problem, and decoupling it from Adobe's specific visual brand is
  exactly what let React Aria become useful (and widely adopted) far
  outside Adobe's own products, unlike React Spectrum itself.

  **Common mistakes:** Only naming the three packages without explaining
  why the split itself was the valuable decision.
</InterviewQuestion>

<InterviewQuestion q="What problem does Shopify's App Bridge solve that a typical internal design system never has to?">
  **What the interviewer is testing:** Whether the candidate understands
  Polaris's unique third-party-extensibility constraint, not just its
  component list.

  **Poor answer:** "It's Polaris's JavaScript library."

  **Good answer:** Explains that App Bridge lets third-party apps embedded
  in the Shopify admin render Polaris-consistent UI without shipping
  Polaris's own React components.

  **Excellent senior answer:** Names the actual mechanism (structured
  cross-frame messaging so the host frame renders native Polaris UI on the
  embedded app's behalf) and why it's necessary — Shopify doesn't control
  third-party developers' code quality or accessibility diligence, but a
  merchant experiences the embedded app as part of Shopify's product, so
  consistency has to be enforced structurally, not by convention.

  **Common mistakes:** Confusing App Bridge with Polaris's regular React
  component library.
</InterviewQuestion>

<InterviewQuestion q="Compare Ant Design's approach to Radix UI's approach and explain when you'd choose each as a foundation.">
  **What the interviewer is testing:** Comparative judgment across the
  headless-vs-styled and opinionated-vs-primitive axes.

  **Poor answer:** "Radix is more modern."

  **Good answer:** Explains Ant Design is a comprehensive, opinionated,
  fully-styled set good for fast, consistent internal tooling; Radix is
  headless, unstyled, behavior-only, good as a foundation under a custom
  visual system.

  **Excellent senior answer:** Ties each to its originating constraint —
  Ant Design to Alibaba's need for many internal teams shipping complex
  admin UI fast with low visual-divergence need; Radix to the goal of
  being reusable under many *different* companies' visual systems — and
  states a concrete deciding factor (need for brand-specific visual
  identity vs. need for shipping speed with low customization).

  **Common mistakes:** Treating one as strictly superior rather than fit
  for different constraints.
</InterviewQuestion>

<InterviewQuestion q="IBM Carbon migrated from Sass to a token/CSS-variable architecture. Why would a mature system take on that migration rather than living with Sass?">
  **What the interviewer is testing:** Understanding of the real,
  practical limitations of build-time-only theming at scale.

  **Poor answer:** "CSS variables are newer than Sass."

  **Good answer:** Explains Sass variables are resolved at build time,
  which makes runtime theme switching (light/dark/multi-brand) require
  separate builds, while CSS custom properties can be swapped at runtime
  via an attribute change.

  **Excellent senior answer:** Adds the design-tooling angle — Sass
  variables have no direct sync path to Figma Variables, while a
  token-driven CSS-variable architecture does, which matters for
  design-to-code sync at Carbon's scale — and frames this as a real,
  costly, in-place migration (not a rewrite), which is a harder and more
  realistic engineering problem than greenfield token architecture design.

  **Common mistakes:** Not knowing the build-time vs. runtime distinction
  between Sass variables and CSS custom properties.
</InterviewQuestion>

<InterviewQuestion q="What is shadcn/ui, and how does its relationship to Radix UI differ from a typical component library dependency?">
  **What the interviewer is testing:** Current knowledge of the component
  distribution landscape, not historical/textbook knowledge.

  **Poor answer:** "It's a UI library like Ant Design."

  **Good answer:** Explains shadcn/ui is a CLI that copies Radix-based,
  Tailwind-styled component source directly into your repo rather than
  installing an npm package.

  **Excellent senior answer:** Explains why that distribution model
  exists — full ownership of the code with no version-lock or override
  constraints a package dependency would impose — and why it was only
  viable *because* Radix had already solved accessible behavior; shadcn/ui
  only had to add the visual layer, which would have been a much larger
  undertaking without Radix as a foundation.

  **Common mistakes:** Describing shadcn/ui as "just another component
  library" without understanding the copy-paste distribution model or its
  dependency on Radix specifically.
</InterviewQuestion>

## Manager-Level Questions

<ManagerQuestion q="If you were starting a new internal design system today, which of these case studies would you borrow most heavily from, and why?">
  **What the interviewer is testing:** Applied synthesis — can the
  candidate map their own org's actual constraint onto the right reference
  point, not just recite case studies.

  **Poor answer:** "I'd copy Material Design, it's the most famous."

  **Good answer:** Picks a system whose constraint plausibly matches the
  org's (e.g., Radix-as-foundation for a small team, Atlassian's semantic
  tokens for a multi-product org) and explains the match.

  **Excellent senior answer:** Explicitly separates what to borrow
  (pattern/constraint-fit) from what not to (scale-inappropriate scope,
  e.g. not attempting Spectrum-level multi-product maturity with a
  three-person team), and names a concrete first deliverable that reflects
  the borrowed pattern rather than staying abstract.

  **Common mistakes:** Picking the most famous or most-liked system
  without justifying constraint fit.
</ManagerQuestion>

<ManagerQuestion q="Shopify has to enforce accessibility standards on UI it doesn't fully control (third-party embedded apps). How would you approach a similar problem if your design system had external consumers you don't manage?">
  **What the interviewer is testing:** Governance and influence thinking
  applied to a structurally hard consistency problem.

  **Poor answer:** "I'd just require them to follow our guidelines."

  **Good answer:** Describes a mix of structural enforcement (something
  like App Bridge, where the host renders the consistent parts natively
  rather than trusting the third party to reimplement them) plus
  documentation and review gates for the parts that can't be structurally
  enforced.

  **Excellent senior answer:** Distinguishes what can be enforced
  *structurally* (the host renders it, so there's nothing to get wrong)
  from what can only be enforced through *incentive and review* (an
  external team's own custom UI), and prioritizes moving as much as
  possible into the structural category, since guideline compliance from
  parties you don't manage is inherently unreliable at scale.

  **Common mistakes:** Relying entirely on documentation/guidelines with
  no structural enforcement mechanism.
</ManagerQuestion>

<ManagerQuestion q="A team on your project pushes to rebuild your component library from scratch rather than adopting Radix as a foundation, arguing 'we need full control.' How do you handle that disagreement?">
  **What the interviewer is testing:** Ability to navigate a build-vs-adopt
  disagreement with data and tradeoff clarity rather than authority.

  **Poor answer:** "I'd just tell them Radix is better."

  **Good answer:** Asks what "full control" actually means in concrete
  terms — is it visual control (which Radix already grants, since it's
  unstyled) or behavioral control (which would mean re-solving accessible
  interaction behavior from scratch)?

  **Excellent senior answer:** Separates the team's real underlying concern
  from the stated position — often "full control" really means fear of
  being blocked by an external dependency's release cadence or breaking
  changes, which is addressable (vendoring the specific version, wrapping
  Radix behind an internal API) without discarding its actual value
  (years of tested accessible behavior). Frames the decision in terms of
  what a from-scratch rebuild would cost in engineering time versus what
  risk it's actually mitigating.

  **Common mistakes:** Treating this as a pure technical debate rather than
  surfacing the real (often risk-aversion or control-related) concern
  driving the "full control" framing.
</ManagerQuestion>

## Summary

The eight systems in this chapter arrived at very different architectures
not because of taste, but because each was solving a different forcing
constraint. Material Design's constraint is platform count (Android, iOS,
Web, Flutter), solved with a token specification treated as the
cross-platform contract, extended by Material You into runtime-resolved
tokens. Atlassian's and Adobe's constraint is product count within one
company, solved with semantic tokens (Atlassian) and a behavior/style split
across React Aria, React Stately, and React Spectrum (Adobe) — a split that
mattered beyond Adobe because it made the hardest, most reusable part of
the problem (accessible behavior) independently valuable. Shopify Polaris's
constraint is unique in this set — third-party developers building into a
runtime Shopify doesn't control — solved structurally with App Bridge
rather than through guidelines alone. IBM Carbon is the chapter's best
real-world example of styling-architecture migration in production,
moving from Sass to a token/CSS-variable model for runtime theming and
Figma sync. Ant Design's comprehensive, opinionated component set and
Radix's headless, unstyled primitives sit at opposite ends of the same
axis, each correct for a different team-size and customization-need
profile. Chakra UI's lasting contribution was normalizing accessible
defaults across the open-source React ecosystem. And Radix's relationship
to shadcn/ui — a foundation other systems, including copy-paste-distributed
ones, now build on top of — is the most current and interview-relevant
development in this space, worth being able to explain precisely.

**Key takeaways**

- Always lead a case-study answer with the *constraint*, not the feature
  list — "X chose Y because of Z constraint" is the shape a strong answer
  takes.
- Material Design solves cross-platform consistency; Atlassian and Adobe
  solve multi-product consistency within one company; Polaris solves
  consistency in a runtime it doesn't control; Carbon demonstrates a real
  in-place styling-architecture migration.
- Adobe's React Aria / React Stately / React Spectrum split — decoupling
  accessible behavior from visual skin — is the single most influential
  architectural pattern in this chapter, and it repeats in Radix.
- Ant Design (comprehensive, opinionated) and Radix (headless, unstyled)
  sit at opposite ends of the same axis; neither is universally better,
  each fits a different team-size and customization profile.
- shadcn/ui is Radix-based components distributed by copy-paste rather
  than npm install — full ownership over version-lock — and it only works
  because Radix already solved accessible behavior.
- When asked to design a new system, match the reference point to the
  actual constraint you have, not the most famous or most-liked system.
